Executive summary

The vision

One GraphX Studio. We are combining the working Craft apps (DesignCraft, VectorCraft, PhotoCraft, PdfCraft, LightCraft; open-source Rust apps we forked and own, PD-53) into one native Rust/egui app that runs in the browser (WebAssembly) and on macOS, Windows and Linux (PD-41, PD-44, PD-48, PD-104). We build on what works rather than rebuild it, and keep a test build live at every step (PD-100). Design is the base; Image, Develop, Vector and PDF Press tools appear when you select that kind of object (PD-69). Everything ends as a press-ready PDF, and the saved file is a real PDF (PD-77). Modes: Design, Edit PDF, Templates & VDP, Production (PD-137). Production is built in: the visualizer's production studios fold in as product modes (PD-70, PD-74), and Studio shares its production code with GraphX Prepress, our replacement for the OneVision system the shop runs today (PD-37, PD-145).

Why, for a print and sign shop

  • One tool from artwork to machine. Designers, prepress staff and customers work on one file in one app, with views by role (PD-66), instead of passing work between separate design apps, a web visualizer and the OneVision system. Files are print-safe: nothing prints differently from what is shown (PD-94; PD-107 is a coordinator rule awaiting owner confirmation, Q7).
  • Previews that match production. Studio's live previews and Prepress run the same shared code, so the preview is meant to match what production makes (PD-145, PD-161).
  • Own the production stack. GraphX Prepress is to replace OneVision: one subscription, and we own the margin (PD-04, PD-37).
  • Works offline and grows with the shop. Desktop uses local resources with no artificial limits (PD-101); a shop can start standalone and later move to GraphX with its data already mapped (PD-147).
  • Designers can automate. A designer records a sequence of actions and saves it as a Prepress automation (PD-145).

Where it stands (2026-10-22)

Works (merged through PR #269): New, Open, Import, Place (Craft files, images, SVG, EPS, PDF, AI), Save and reopen; page-by-page canvas; text; colour strip; dockable toolbars and palettes; property bar part 1; in-app Feedback; desktop sign-in; hardened PDF reading with exact file errors.

Not yet: Export (PDF, PNG, SVG, JPEG), the biggest gap; most of the property bar; vector and photo tool families (6 of 90 VectorCraft tools); PDF-as-vector fallback; system fonts; signed builds (Windows and macOS never run on a real machine); updater. Test sites lag the code. Building is paused until Sat Oct 24, 23:00 UTC (PD-112).

Tracker (Progress Checklist, 2026-10-22): 290 tasks: 59 Done, 6 Partial, 157 Not started, 68 Blocked (51 of them production integration, held by PD-118).

Studio modes and phases

  • Modes (PD-137): Design, Edit PDF, Templates & VDP (the former PDF Block Builder), Production.
  • Tool sets inside Design (PD-69, PD-75): Image, Develop, Vector and PDF Press appear when you select that kind of object; their basic create tools always sit in the left toolbar.
  • Phases around Design (PD-63, PD-69): before or during: Templates, Assets; after: Preflight, Prepress, Proof. Each phase is hidden until a real provider backs it (#242).
  • Product modes (PD-70): a production studio is a specialised panel that sets up the canvas (template, dieline, panels) and shares the one Objects panel.
  • Open: how the four PD-137 modes map onto the PD-63/PD-69 phases and tool sets is not yet written down; ask before building mode switching.

Providers: Request proof and Add to order

Studio never calls a service directly. It calls a provider or port, and a control is hidden, with a reason, when no provider is connected. The primary split button defaults by context: Add to order for an orderable product with a live price, Request proof in quote mode or when proof is required, otherwise Save/Export (PD-80). The provider traits exist in code; none is connected yet, so today the button is always Save/Export.

PrepressPort and job tickets

Work leaves Studio as a job ticket through PrepressPort, and results come back as visualisations in Studio: proofs, separations, nesting previews, preflight reports (PD-71). The ticket format is graphx.jobticket/v1 (canonical JSON plus SHA-256, from the Rust job format decided in ADR-0001 D14). The working plan in doc 11 is that Studio v1 shows advisory previews and writes no machine files, with production outputs made in Prepress; who writes cutter and machine files is still an owner question (PRD-15, Q5) (doc 11, Big picture). Until Prepress reaches parity, jobs go to the existing OneVision lines through their API (PD-05, PD-144).

Action palette and recorded flows

Studio and Prepress share the exact same processes (PD-145). Every Prepress module is described by one manifest and appears in Studio's Action palette. A designer records a sequence of actions as a flow and saves it as a Prepress automation. It works both ways: Studio functions such as paneling, finishing geometry, dielines and colour fixes are packaged as Prepress modules, and Studio can run code actions over the same module API (PD-146). Codex drafts the manifest; Claude reviews it for the Studio side: palette, recording, undo (PD-165).

Shared reference data

GraphX owns the production reference data: machines and devices, materials (with real roll widths, PD-121), spot and process mappings (PD-120), processes and finishing, device profiles (overcut PD-123, platens PD-124) and catalogs (PD-146, PD-147). Local installs of Studio and Prepress keep a shadow database with the same schema and stable IDs, synced per tenant. A shop that starts standalone can sign up for GraphX and migrate with every record already mapped. Databases are PostgreSQL only, local installs included (PD-152); ADR-0001's SQLite local store is superseded by PD-152. Entities E1 to E6 and crate SC-13 are in Prepress cross-reference.

One PDF, colour and conversion engine

There are at least five PDF stacks today. They converge into one PDF engine in graphx-production-core (PD-154): Studio's hardened reading, rendering and writing, plus Prepress's structural editing, with one limits policy, one hostile-file corpus and one diagnostics table. One colour crate gives the same colour for the same input and profile everywhere (PD-161), with the colour behaviour of the OneVision system we are replacing as the reference (PD-163). One image/PDF conversion crate serves Studio Open, Place and Export and Prepress rasterizing (PD-162). Each app migrates behind its current interface; Studio's baseline is not blocked (PD-154). Design: production-inventory/shared-pdf-engine-design.md (draft).

Who builds the shared crates

Every shared crate is joint (PD-166). Claude builds and proves a capability in Studio, Codex in Prepress; then both combine it into graphx-production-core, confer on the board, and the other side reviews every change. Older documents that assign a single builder per crate are superseded on that point. The repo exists with a scaffold PR open (PD-155).

Production integration comes after the baseline

Studio-side production integration work (PRD tasks, every phase) starts only after the Studio baseline design system is built and approved by the owner; production modes then build on those Studio systems (PD-118). PD-118 gates only that Studio UI integration. Prepress is not held: Codex continues the Prepress rebuild now and shared-crate work proceeds with it (PD-151, PD-155). Doc 11 still says Prepress parity is "assumed not gated"; PD-151 settles it (doc 11).

Product requirements (PRD)

Problem

A print and sign shop's work crosses many tools: design apps, a web visualizer with about 40 production prototypes, a proofing service, an online store, and the OneVision system that drives the machines. Files and decisions are re-entered at each hand-off, previews and production do not run the same code, and the shop pays for and depends on outside production software. The Craft apps already work, but as five separate apps.

Goals

  • Ship the full v1 of GraphX Studio, all of it, with no slice-first release (PD-44): Design with Image, Develop, Vector and PDF Press; DAM core (PD-47); desktop (PD-48); large-file support.
  • Keep a working test build live at all times so designers can use it and report in the app (PD-100, PD-104, PD-105).
  • Make Studio the design and production front end of GraphX, sharing code with GraphX Prepress (PD-145 to PD-147).
  • Replace the OneVision system in production step by step, each piece shadow-proven first (PD-04, PD-143, PD-151).

Non-goals (now)

  • Rebuilding what the Craft apps already do (PD-100).
  • Studio writing machine files in v1: production outputs come from Prepress (doc 11).
  • Remote AI image generation in v1 (PD-82 item 12).
  • Being a compliance engine: no licence checks on fonts (PD-114); licences for other content wait until customer launch (PD-126, PD-136).
  • Claiming ADA compliance: only "Meets the checked ADA rules" (PD-81).
  • Studio-side production integration before the baseline is approved (PD-118); DAM server, large-file pipeline and other NOT NOW items before "working" (STUDIO-PLAN).

Functional requirements (FRD)

Each requirement is one line, with a link to the module doc that holds the detail. Read the linked doc before building; do not copy its content into code comments or PRs, link it.

  • ID: FR-<area>-<nn>. IDs are stable; new requirements take the next number.
  • Priority: Must = needed for the baseline or a decided rule that applies to all work; Should = decided, but scheduled after the baseline; Could = idea, open or later. Priorities are this doc's reading of the sources, not owner rulings; the owner may change them.
  • Source: owner decision IDs from the Ideas & Decisions Register (PD, UX, TP, PR, AR, CM), tracker task IDs, or STUDIO-PLAN.
  • Detail: each area names its module doc; the colour area is in doc 4, text and fonts in doc 5, proofing and production in doc 11.
  • Status (from the tracker sheet and module docs, 2026-10-21/22): Built = merged; Partial = some of it merged; Not started; Blocked = waiting on a named decision, input or gate (PD-118 is the production-integration gate). Not verified = no tracker row or doc states it; treat as not built until checked.

How we work

The project rules are in the workspace AGENTS.md on the build server (/mnt/data-d/dev/GraphXCPI/AGENTS.md) and each repo's own AGENTS.md. They were written for AI agent lanes and apply to every contributor. How human developers fit the lane and review model is open (Q1); until the owner rules, follow the rules below and ask before merging.

  • GraphXCPI is the only development organisation. Never work on main or master; never force-push or rewrite history; no batch merges.
  • Branch names use the crd/ prefix with a task name. One PR per concern.

Worktrees

  • repos/<repo> is a clean anchor on the default branch. Never edit in an anchor.
  • worktrees/<repo>/<task> holds each active branch. Create worktrees with absolute paths. Never create clones under /tmp or the Docker deployment folders.
  • Never delete a worktree without recording its branch, commit, dirty state and a verified recovery copy.

CodeGraph

  • Use CodeGraph before editing (PD-84): codegraph query to find code, then codegraph callers and codegraph callees on every symbol you change.
  • Shared read-only maps: worktrees/<repo>/codemap for graphx-studio, graphx-visualizer, graphx-prepress and graphx-production-core, refreshed by a timer every 10 minutes. Never edit them.
  • In your own worktree, build a local index with codegraph init -i or codegraph sync.
  • Every PR lists the modules it calls and is called by, from CodeGraph, plus the user action that triggers the changed code.

  • No GitHub Actions, in any form: not as a gate, not proposed, not re-run. The merge gate is local verification (the repo's own checks, for Studio cargo xtask ci) plus reviews plus approval, recorded in a PR comment.
  • Reviews state the verdict first, then numbered blockers with file:line and a one-line fix. Freeze the diff hash while it is under review.
  • Every PR follows PD-84: //! headers, rustdoc, small files, concept folders, CodeGraph connection list. Missing docs or an oversized new file is a MAJOR finding.

Tracker, module docs and decisions

  • The Progress Checklist sheet is the task ledger. States: Not started, Partial, Needs verification, Blocked, Done. Done means the whole task and its done-test are verified, with evidence in the cell note. Set Started and Partial when you begin; Finished, Elapsed and Done when it merges. Record retries, review rounds and any rabbit hole.
  • The 11 module docs explain behaviour and evidence. Update the doc and the sheet together. HTML sources are in coordination/module-docs/ and are republished as tabs.
  • The Ideas & Decisions Register (coordination/OWNER-IDEAS.md) records every owner decision, append-only, the same day it is given.
  • Use the graphx-project-update skill for tracker and doc updates and graphx-project-read for status. Skills live in the shared skills repo.

Coordination board, lanes and the working agreement

  • coordination/ONE-APP.md is the Claude and Codex board: posts of at most 10 lines, "FROM → TO: topic — ACTION NEEDED | FYI", one Asks line. Status lives in the trackers, not the board.
  • Lanes: Claude works in Studio, Codex in Prepress (including extraction); shared crates are joint (PD-166). Design, plan and build are split roughly half and half, and the reviewer is always the other family (PD-89).
  • coordination/WORKING-AGREEMENT.md (v3, agreed 2026-10-22, PD-169, PD-170): two strikes stop an approach; timebox with an exit artifact; decide before researching; no speculative work on paused lanes; one writer per artifact; one definition per thing; smallest proof first; batch owner questions with a recommendation.
  • coordination/FACTS.md holds stable paths, IDs and commands. Read it before rediscovering anything.

Picking up a task

  • 1. Take the next ready row: the STUDIO-PLAN FOCUS list in order, then section 4 of STUDIO-PLAN. Check the board and tracker to see whether someone already has it.
  • 2. Read the done-test in STUDIO-PLAN section 4 and close its owner questions first.
  • 3. Create a worktree from the integration branch; query CodeGraph; set the row to Partial with a start time.
  • 4. Build the smallest change that passes the done-test; run the targeted check, then the full gate before review.
  • 5. Open the PR with the CodeGraph connection list and the triggering user action; get one cross-family review.
  • 6. Merge per the rules; refresh the test build; mark the row Done with evidence; update the module doc.
  • If you are blocked, write the exact missing input in the cell note, tell the owner, and take the next ready item.

  • Day 3: read the module docs for your area and its CRAFT-PARITY-GAPS rows; read docs/architecture in graphx-studio.
  • Days 4 to 5: take one S-size ready task end to end (worktree, CodeGraph, PR, review, merge, tracker, doc).
